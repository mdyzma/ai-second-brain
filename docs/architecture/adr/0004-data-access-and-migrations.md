# ADR-0004: Data access with psycopg 3 (async) + explicit SQL; schema via dbmate

**Status:** Proposed
**Date:** 2026-09-29
**Deciders:** Michal Dyzma

## Context

Greenfield, and PostgreSQL is the primary storage. The prompt suggests SQLAlchemy 2.0 + asyncpg. The important queries are SQL-heavy: hybrid RRF search, recursive CTEs, `halfvec` expression HNSW indexes, `SKIP LOCKED` jobs, generated `tsvector` columns. Migrations must be runnable from `just` on Windows (dev), Linux (Proxmox) and CI, and must stay the single source of truth for a schema that more than one language might read. That includes the eval harness today, and possibly TypeScript later ([ADR-0011](0011-backend-language-python-vs-typescript.md)).

## Decision

- **Schema:** plain SQL migrations in `db/migrations/`, applied with **dbmate** (single binary, language-neutral, `up`/`down`/`status`, dumps `db/schema.sql` for review). Recipes: `just db::migrate`, `just db::new <name>`, `just db::rollback`, `just db::reset`.
- **Access:** **psycopg 3** with its async connection pool in the API, sync in scripts. SQL lives in per-module repository classes. Rows map to Pydantic models. The `pgvector` Python adapter handles vector/halfvec types.
- Every repository has integration tests against real Postgres (the compose `pgvector/pgvector:pg17` image, fresh schema per test session).

## Options Considered

| Option | Pros | Cons |
|---|---|---|
| **A. psycopg 3 + SQL + dbmate (chosen)** | Advanced SQL stays readable; one driver for sync and async; migrations are language-neutral | Manual row mapping; no autogenerate |
| B. SQLAlchemy 2.0 (ORM) + asyncpg + Alembic | Autogenerated migrations, typed models | pgvector/FTS/RRF end up in `text()` anyway; Alembic ties schema to Python; asyncpg + pgvector needs separate codec setup |
| C. SQLAlchemy **Core** + psycopg + Alembic | Composable query builder | Same Alembic lock-in; builder adds little to hand-written analytic SQL |
| D. yoyo-migrations | Python-native, simple | Python-only; dbmate fits the "just across stack" model better |

## Consequences

- Easier: reading and reviewing every query; sharing the schema with non-Python tools.
- Harder: repetitive CRUD. Revisit SQLAlchemy Core if CRUD tables multiply past ~25.
- Rule: application code never runs DDL; only dbmate migrations do.
